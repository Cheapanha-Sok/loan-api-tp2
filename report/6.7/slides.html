One design decision I would defend

Run the tests inside the image build

  • The test stage in Dockerfile.prod runs pytest against the exact code and model file that will ship.
  • The runtime stage copies a marker from it, so a red test means no image and no deploy, on any builder.
  • Proven in drill 1: PR #3 merged, Render build failed, production stayed on the old SHA.

Why it matters

When GitHub Actions was locked by a billing issue, the release gate did not disappear with it. CI moved into the artifact itself, so the guarantee "only tested code goes live" held without any CI service.

Plus: deploys are verified by commit

/health reports git_sha; "healthy" alone is not proof, because the old version is healthy too.

One trade-off I accepted

Render's free Git pipeline instead of the full GitHub pipeline

What I gained

A working, automatic test → build → deploy → health-check pipeline the same day, at zero cost, with HTTPS, logs and one-click rollback, despite the account lock.

What I gave up

No branch protection (it needs a CI status check), no SHA-tagged images in GHCR, and verify runs from my terminal instead of a CI job. Render rebuilds on every deploy, and a rollback switches auto-deploy off until re-enabled.

  • Also accepted: free-plan cold starts (about a minute after 15 idle minutes) and an in-memory application store that resets on every deploy.
  • Fine for a course project; a paying lender would get a paid instance and PostgreSQL.

The real fix

test_risky_applicant_scores_higher_than_safe_applicant: a risky borrower must score higher than a safe one and the band must agree with the probability. It fails on the inverted code (1 failed, 7 passed), so the same mistake can never ship again.
